# Deploying the test run to Render (app on Render, model on a Colab GPU)

For a **demo with synthetic data**. Render hosts the app and a PostgreSQL database; the Gyan SLM and the
embedding model run on the Colab A100 from `DEPLOY_COLAB.md`. Render has no GPU and no India region, so
nothing real (no student data) belongs here; the production target stays an in-state deployment.

```
Browser -> Render web service (Docker, this repo) -> Render PostgreSQL
                    |
                    +--HTTPS + Bearer token--> Cloudflare tunnel -> Colab A100 (Ollama: Gemma 4 + bge-m3)
```

Everything Render needs is in `render.yaml` (a Blueprint): service, database, environment variables.

## Before you start

1. A GitHub repo Render can read, with these changes pushed (the remote today is
   `github.com/vishrutxraj/HAMAR_Shiksha`; you need push access, or fork it and use the fork).
2. The Colab notebook running, so you have the **tunnel URL** and **token** it printed (`colab/hamar_gyan_gpu.ipynb`).
3. A Render account with GitHub connected (Dashboard > Account Settings > GitHub).

## Steps

1. **Push the code.**
   ```powershell
   git add -A ; git commit -m "Render blueprint, remote GPU runtime" ; git push origin main
   ```
2. **Create the Blueprint.** Render Dashboard > **New > Blueprint** > pick the repo and branch. Render reads
   `render.yaml` and lists one web service (`hamar-shiksha`) and one database (`hamar-db`).
3. **Fill the two secrets it asks for** (the `sync: false` variables):
   - `HS_SLM_URL` = the `https://....trycloudflare.com` URL from the notebook (no trailing path)
   - `HS_SLM_API_KEY` = the token from the notebook

   `HS_SECRET_KEY` is generated by Render; the database URL is wired in automatically.
4. **Apply.** The first build takes a few minutes (Docker image + Python packages). In the service's **Logs**
   you should see, in order: `database migrated`, the demo-seed summary (about 1-3 minutes on the first boot
   only), `Application startup complete`. Render marks it live once `/api/health` answers.
5. **Check it works.**
   - Open `https://<service>.onrender.com/api/health` -> `{"status":"ok","environment":"demo",...}`
   - Sign in with a demo account (`docs/DEMO_ACCOUNTS.md`, e.g. student `st-demo01` / `Demo@Student26`).
   - Ask Gyan a curriculum question (Hindi or English). A cited, "verified" answer means the GPU path works;
     a labelled textbook-passage fallback means Render cannot reach the model (see Troubleshooting).
6. **Each time the Colab notebook restarts**, the URL (and the token, unless you set the `HS_GPU_TOKEN`
   Colab secret) change: Dashboard > service > **Environment** > edit `HS_SLM_URL` / `HS_SLM_API_KEY` >
   **Save and deploy** (a rebuild is not needed for environment-only changes).
7. **When finished**, suspend or delete the service and database (Settings > Suspend / Delete), and stop the
   Colab runtime.

## What was adapted for Render

| Concern | What happens |
|---|---|
| Port | Render gives the container `PORT` (default 10000) and checks that port. The image now listens on `$PORT` (8000 when unset, as in docker compose). Do not set `PORT` yourself. |
| Database URL | Render provides `postgresql://...`; `app/config.py` rewrites it to `postgresql+psycopg://` (psycopg 3). |
| Migrations / demo data | `docker/entrypoint.sh` runs migrations on every boot and `seed-demo` when `HS_SEED_DEMO=1`; seeding is skipped when the data already exists. |
| Workers | `WEB_CONCURRENCY=1` for the 512 MB free instance (the image defaults to 2). |
| Demo data size | `HS_DEMO_SCALE=compact` (about 1,100 users, 57 schools, 33 districts). The `full` set (about 3,000 students) peaks near 550 MB while seeding, so a 512 MB instance is killed ("Out of memory (used over 512Mi)") before it ever opens a port. |
| Accounts file | The seed also writes `docs/DEMO_ACCOUNTS.md`; the image has no `docs/` folder, so that write is now skipped instead of aborting the boot. Use the accounts below. |
| Environment name | `HS_ENVIRONMENT=demo`. `production` refuses demo data, so a demo cannot use it. API docs (`/api/docs`) stay reachable in `demo`. |
| Health check | `healthCheckPath: /api/health` (also touches the database). |
| Reasoning model | `HS_SLM_THINK=false` stops Gemma 4 spending the answer budget on hidden reasoning. |

## Limits of the free plan (check Render's current terms)

- The web service **sleeps after 15 minutes** without traffic; the next request takes about a minute.
- The filesystem is **wiped on every restart**: the textbook vector cache (`HS_KB_DIR`) is rebuilt, so the first
  question after a restart re-embeds the demo passages through the tunnel (a few seconds). If the GPU is down at
  that moment the app answers with keyword search and retries embeddings every minute.
- The free **database expires 30 days** after creation (14-day grace), 1 GB, no backups.
- 512 MB RAM. If the service is killed for memory, move it to a paid plan in `render.yaml` (`plan: starter`) and raise `WEB_CONCURRENCY`.
- The real SCERT textbooks are not in the image (PDFs are fetched by `scripts/fetch_scert_cg.py`); the demo
  curriculum is. Ingesting the full set on Render needs a persistent disk (paid) and is not part of this test.

## Cautions

- The URL is public and the demo passwords are published in the repo. Anyone who finds it can sign in and spend
  your Colab GPU time. Share the link narrowly and delete the service afterwards.
- Questions typed into the app are sent to the Colab VM (Google). Demo data only.
- Treat `HS_SLM_API_KEY` like a password; it is stored in Render's environment, not in Git.

## Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| Deploy fails: "Refusing to start in production" | `HS_ENVIRONMENT` was set to `production`; use `demo` for this test. |
| Log says `Out of memory (used over 512Mi)` | The full demo data set was being seeded. Keep `HS_DEMO_SCALE=compact`, or move the service to a paid plan with more RAM. |
| "Waiting for internal health check ... :10000/api/health" never ends | The app is listening on a different port than Render checks. Open the service's Environment tab and delete any `PORT` variable you or an older blueprint added, then redeploy. Also confirm the logs reach `Application startup complete`. |
| `/api/health` 500 | Database not reachable yet; redeploy after the database shows "Available". |
| Gyan answers are textbook passages labelled non-AI | Render cannot reach Colab: notebook stopped, URL/token stale (step 6), or the tunnel was recreated. Check `https://<tunnel>/health`. |
| 401/403 in the Colab proxy log | Wrong token in `HS_SLM_API_KEY`. |
| HTTP 524 / timeouts on the first question | The model was not loaded on Colab (idle unload or restart). Re-run the warm-up cell (6b); see `DEPLOY_COLAB.md`. |
| Answers empty or very slow at first | Model still loading on Colab (first request); `HS_SLM_TIMEOUT_SECONDS` is 300. |
